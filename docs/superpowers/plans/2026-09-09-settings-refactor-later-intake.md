### Task 5 concrete design: scoped saved-loop order

September 9, 2026 independent source audit. This resolves the remaining implementation choices within the approved actor/library/song model; no new approval gate or migration number is introduced.

**Live owners and authority.** `services/saved_loops_postgres.py` currently hardcodes `_bootstrap_context_sql`, and `services/loops.py` performs collection-wide read/replace for add, delete and reorder. Replace request-facing calls with explicit scope arguments obtained through `current_actor_from_request(request)`: authenticated `account_id` and `current_library_id`, with the current-library relationship required by `policy_asgi._library_scope`. Never accept either ID from JSON/query parameters and never fall back to the bootstrap owner. Keep existing route capability/CSRF boundaries. Pass the same scope into `/utilities/loops`, all four mutation routes in `api_wave_b_asgi_routes.py`, media and preview GETs in `web_asgi.py`, and the loop-ID branch of `/playback/waveform` in `playback_stream_asgi.py`. The waveform branch is an additional live caller that must not be missed. Bootstrap importer/test compatibility may retain an explicitly named legacy adapter path; no authenticated route may invoke it.

**Stable song identity and historical rows.** `app.saved_loops` already has account/library/track/parent foreign keys, nullable track IDs, and a partial unique `(account_id, library_id, loop_key)` index after migration 0018. Keep every existing database ID and public loop key. Use the persisted `library.local_tracks.id` as relational song identity and expose an opaque-to-the-UI `song_key` such as `track:<id>`; resolve it back to a track in the current library on every mutation. This avoids leaking or depending on potentially path-shaped `track_key` values, metadata titles or normalized artist/album collisions. Direct creation derives track ID from the normalized, authorized source file's exact `local_track_files` mapping in that library, requiring one distinct track ID. Nested creation derives it from the same-owner/library parent. Client artist/title/album and client song key never establish creation ownership.

A forward backfill may fill a null track ID only from a same-scope, cycle-free parent chain or one distinct exact source-file mapping. Do not repeat migration 0018's metadata-title fallback or its newest-row tie breaker for ambiguous paths. Preserve existing non-null valid relationships; validate their track belongs to the row's library. Unknown, ambiguous or invalid relationships stay retained and visible to their owning account as `song_identity_status: unresolved`, `song_key: null`, `order_revision: null`, `can_reorder: false`. Give each unresolved loop a client-only `unresolved:<loop-id>` navigation key so display text cannot merge unrelated loops. Its saved media and authorized deletion remain available; creating descendants/reordering requires resolved trustworthy song identity. Rows with null account/library remain retained but are never claimed by whichever user logs in next.

**Revision storage and migration.** Add `app.saved_loop_orders(account_id, library_id, track_id, revision bigint not null default 0 check (revision >= 0), updated_at)` with primary key `(account_id, library_id, track_id)` and normal account/library/track foreign keys. Add a scoped active-loop lookup index on `(account_id, library_id, track_id)` with the existing non-removed predicate. Follow current migration grants for app/migrator roles. Backfill one revision-zero row per valid existing song group and preserve each group's existing order by sorting valid `metadata.source_index`, then `created_at desc`, then loop key. Reuse `metadata.source_index` as the per-song position rather than add a second competing order field; update only that JSON member and `updated_at`. Leave unrelated metadata/source coordinates intact. Keep revision rows after the last loop is removed so an empty song cannot reset its concurrency token. Inspect current migration maximum immediately before authoring; no number is reserved here.

**Atomic mutation protocol.** Reorder JSON is `{song_key, expected_revision, ordered_ids}`. Require a nonnegative integer revision and a list of nonempty unique string IDs; reject malformed input with 400. In one transaction, resolve the current-library track, insert the song revision row on conflict do nothing, and select that exact row `FOR UPDATE`. Select current active loop membership using all three scope columns. Unknown song or foreign resource returns 404; stale revision returns 409 with only that actor's current song revision/order; incomplete/foreign/duplicate membership never gets silently appended or dropped. Compare the exact ID set and length before any write. A valid identical order is a no-op retaining its revision. Otherwise update only that song's positions and increment revision once, returning the committed snapshot from the transaction. All writers acquire the revision row before changing loop membership; never acquire loop locks first and then the song lock.

Creation performs expensive FFmpeg work outside the database lock into a unique owned output, then takes the same song lock, revalidates the source/parent's scope and active membership, inserts exactly one loop at the front (preserving current creation behavior), shifts that song's positions and increments revision. On failed authoritative insertion, remove only the newly created owned artifact. Deletion resolves its scoped target, locks the resolved song row, rechecks the target, tombstones only that loop, compacts that song's positions and increments revision. Retain tombstone metadata/original coordinates for historical ancestor evidence. Unresolved-loop deletion locks only that exact scoped loop row and cannot change a resolved group's revision. A create/delete committed before reorder makes the old token stale; one committed afterwards builds on the new order. No collection-wide replacement remains in these paths.

**Media and preview containment.** Capability approval alone does not prove loop ownership. Resolve a live scoped row before opening its audio, producing a pitch preview, serving a cached preview, or returning waveform data; missing/foreign/removed IDs all return 404. The current preview GET checks only a filename, so it needs this ownership lookup too. Parse existing `<loop-id>_pplusN`/`_pminusN` IDs with a strict anchored suffix and valid pitch range, then verify the derived scoped loop; do not sanitize malformed identifiers into a different valid name. Because loop keys are unique per scope while current filenames are global, put new loop/preview artifacts in server-derived account/library subdirectories. Resolve existing stored legacy paths only under their approved loop roots after ownership lookup; do not prefer a global canonical filename belonging to another scope. Reject ambiguous cross-scope legacy artifact references rather than transfer ownership. Preserve legacy IDs/bytes and avoid eager file moves. Recheck active ownership after preview generation; deletion during generation cannot make a newly cached artifact publicly readable. Cleanup may remove only files belonging to the deleted scoped loop, never another account's same-named artifact.

**Read projection and frontend reconciliation.** Return existing loop fields plus `song_key`, `song_identity_status` and per-song `order_revision` (or an equivalent `song_orders` map), and fresh current-request `allowed_actions`. Do not reuse another actor's cached permission projection. Group by `song_key`; stop normalized metadata/path grouping. The only durable drag is a loop panel within its song; remove the old group-to-group global reorder mutation. Parent navigation order can remain deterministic display order. Pointer and accessible Move Up/Down use the identical per-song payload and mutation; suppress same-position, cross-song, outside and cancelled drops before fetching.

Replace `rerenderUtilityLoopListOnly` for order changes: it currently calls full `renderUtilityModalContent` during optimism, success and rollback, remounting audio. Snapshot the affected ID order/revision and move existing panel nodes and corresponding tree children with `insertBefore`/`appendChild`; retain audio elements, controllers, waveform canvases, range edit state, focus and scroll. Use before/after element rectangles for neighbor motion, an insertion cue and reduced-motion handling. One pending reorder per song prevents overlapping optimistic snapshots. Success reconciles server order by moving those same nodes; failure restores prior order likewise, while a 409 can then reconcile the authorized latest membership without replacing unaffected players. A removed loop alone is disposed; new loop IDs alone create new panels. A stale response after switching tabs/songs must not remount the current unrelated view.
